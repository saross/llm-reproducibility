## Findings

### F1. T15's Q5 provenance is unsupported

T15 is the named value that the Ertebølle-cluster ornament strings occur on
only ten objects (p. 7, §5; also the Table 3 caption). The ids shifted
between attempts, and this plan's T17 is a different target, the motifs with
the highest individual frequencies.

T15's method is a labelled verification aid that counts the objects in
`data` carrying at least two of C4, C5, C12, C13, and D7, a selection rule
inferred from Table 3. That is the method attempt 04 used. The plan states
Q5's `inputs-from-authors-code` as `yes`, with the evidence "Presence
columns are read from `data` created by executing the authors' PART 1."

PART 1 of the deposited `Herskind&Riede_S2.R` (lines 19 to 32) loads
packages and runs one data statement, `data <- read_excel("Herskind&Riede_S1.xlsx")`
(line 30). It derives nothing. The five motifs are already columns of the
deposited S1 `Data` sheet (290 columns; checked with openpyxl on the
planner's own download of Zenodo record 10801706, version 2). T15's inputs
are therefore deposited data passed through a file read, and the condition
the rule names, "it is credited only where its inputs come from executing
the authors' code", does not hold.

The planner knew what PART 1 does. Its T03 evidence reads "`data`, the
object created by executing the authors' PART 1 (read_excel on the
deposited S1)". It read loading the deposit as executing the authors' code,
applied that reading to every Q5 target, and asked the approver about it
directly, "Approve this reading of the inputs-from-authors-code condition?"
The contract worked as far as surfacing the question. It did not stop the
planner from claiming credit under its own reading while the question was
open.

Among the targets the planner named as inferred aid rules, T15 rests on
`data` alone. T06 is mixed. Its cell set and pointwise mutual information
come from the PART 7 `bigrams` object, and its per-object chronology and
motif presence come from `data`. T11, T13, T14, and T17 draw on objects the
authors' code computes. Any re-plan should have T06 checked as T15 was.

**Implication for the rule.** The condition's text admits the planner's
reading, but the rule need not change. Q5's ruling (executed-code audit,
2026-10-05; `executed-code-audit-2026-10-04/findings.json`,
`question_rulings[4]`) credited Key et al.'s inferred Extension % formula
"only where its OLE inputs come from executing the authors' code": inputs
the authors' script computes, not data it loads. Rewording the condition
would amend a lodged rule (the registry's clauses are verbatim, and
`tests/test_rulings.py` checks them against the lodged text). Recording
the registrant's reading beside the condition does not; see "The
long-term fix" below.

### F4. Two gaps in the run audit

The audit's `writes_outside_scope` is built from `write_targets()`
(`scripts/reproduction-lane.py`, lines 8162 to 8179, used at 8306 to 8310),
which counts only Write, Edit, and NotebookEdit tool calls. The planner's
tools are Read, Grep, Glob, and Bash, so for a planner the check cannot
fire. This planner wrote two helper scripts by shell heredoc into the
harness scratchpad (`scratchpad/scripts/inspect_xlsx.py` and
`row_population.py`), outside its attempt and scratch directories, and the
audit reported none. The shell-write parser `segment_writes()` (line 8667)
exists and is used by the executor's write-provenance check (line 8912).

The audit's blinding scan of command output uses `path_tokens()` (lines
8206 to 8209), which keeps only tokens containing `/` or ending in `.json`,
`.md`, or `.csv`. An `ls` of `reproduction-system/` printed the bare name
`lodged-rules.yaml`, and the audit raised no warning. The planner reported
the listing itself, in its questions to the approver. The same filter
applies to the command itself, and `file_accesses()`
(`scripts/reconcile-run.py` line 213) covers only Read, Grep, and Glob, so
a Bash read of a blinded file by its bare name is missed outright:
checked against this run's blinding set,
`cd …/reproduction-system && cat lodged-rules.yaml` gives no hit, while
`cat reproduction-system/lodged-rules.yaml` is caught. This planner's
transcript shows no such read (no call names the registry, and no result
carries text found only in it), so the run is unaffected; the gap is the
audit's.

## The long-term fix (proposed 2026-10-21, for Astra's scoping)

Gate 1.3.1's finding (an approved plan dropped Q5's input condition) and
F1 are one failure at two depths. The registry asks the planner for a
verdict on a condition worded so that one reading makes it trivially true,
and the lane checks only that a verdict and some evidence exist. Only the
approver checks truth, and in gate 1.3.1 two approvals missed it. The
principle: the planner states facts, the lane derives the condition, and
credit carries the burden of proof.

1. **The registrant's reading, recorded beside the condition.** Approved by
   Shawn on 2026-10-21, to enter the registry with the fix's PR:

   > An input comes from executing the authors' code when the planned
   > method takes it from a result the authors' code computes in the run:
   > an estimate, count, table, or other product of its calculations. A
   > value the planned method takes from a deposited file, directly or
   > through the authors' code loading, selecting, filtering, renaming, or
   > retyping it, is deposited data, and the condition does not hold. What
   > decides is where the method takes the value from, not whether a copy
   > exists elsewhere: a count the authors' code computes in the run
   > qualifies even where the deposit also tabulates it.

   Its basis is Q5's own case (Key et al.'s OLE estimates, computed by the
   authors' script), the 2026-10-17 ruling on attempt 04's T17, and ruling
   1 here. It has the status of the condition lists Shawn approved on
   2026-10-19, a reading rather than an amendment, and the lodged text is
   unchanged.
2. **Lineage, not verdicts.** For each input an inferred formula uses, the
   plan declares the object and its source: a deposited file and column, a
   statement of the authors' code (file and lines) that computes it, a
   printed value, or a reconstruction. The lane derives
   `inputs-from-authors-code` from those declarations and refuses a
   "computed by" citation whose lines only load data, against a short
   per-language list of loading functions. T15 would have had to cite
   `Herskind&Riede_S2.R` line 30, a `read_excel` call.
3. **Credit carries the burden.** A plan does not claim credit on a reading
   it asks the approver to accept: a target whose credit turns on an open
   question is planned not-creditable. Accepting the permissive reading
   then costs a re-plan, since a ruling never creates credit. For a study
   of reproducibility that is the right direction of error.
4. **Optional: an independent check before lock.** A fresh-context
   verifier, limited to targets resting on an inferred formula, checks the
   cited lines, and a disagreement goes to the approver.

Each real misapplication becomes a permanent negative fixture (T15 here,
beside attempt 04's T17). Three of the registry's five conditions are
settled at planning, all of them Q5's. The two settled at execution (Q5
`printed-inputs`, R2 `inputs-unobtainable`) take the same shape with the
executor declaring the facts. Parts 2 and 3 change the registry, the plan
schema, the planner definition, and the lane checks, so they go by branch
and PR with Astra's review, then a re-plan under its own API gate,
estimated from this run's basis (F2), to test whether a planner writes the
not-creditable application itself.
